Row-Group Control, Faster S3 Reads, Footer Caching: Hardwood 1.1.0.Beta2 Is Out

I’m happy to announce the release of Hardwood 1.1.0.Beta2! The latest version of the Hardwood open-source library for reading and writing Apache Parquet files brings new features for the writer, significantly improves performance for many different workloads, provides a new API for caching and reusing Parquet file footers, id-based dictionary access, and much more. You can retrieve Hardwood from Maven Central; for the platform-specific CLI binaries check out our GitHub Releases page.

Writer Improvements

By default, the size of row groups emitted by the Hardwood file writer is driven by configurable limits to the row count and working set size. You now can also control row group boundaries more explicitly by calling endRowGroup(), for instance to make sure there’s a new row group for each month in a data set with ordered events:

try (ParquetFileWriter writer = ParquetFileWriter.create(

    RowWriter rows = writer.rowWriter();

    for (Event event : eventsSortedByDay) {
        YearMonth month = YearMonth.from(event.day());
        if (!month.equals(currentMonth)) {
            writer.endRowGroup(); (1)
        }
        currentMonth = month;

        rows.writeRow(row -> row
                .setDate("day", event.day())
                .setLong("id", event.id())
                .setString("payload", event.payload()));
    }
}
1 Close the current row group whenever the month changes, so that each row group holds the events of one month

That way, a query like day >= 2026-10-01 AND day < 2026-11-01 reads exactly the row groups of October, and no row group mixes events of two months.

try (ParquetFileWriter writer =

    RowWriter rows = writer.rowWriter();
    for (Person person : people) {
        RowWriteResult result = rows.tryWriteRow(row -> row
                .setLong("id", person.id())
                .setString("name", person.name()));

        if (result instanceof RowWriteResult.Rejected rejected) {
            System.err.println("Skipped " + person.id() + ": "
                    + rejected.message());
        }
    }
}

A record which the schema can’t hold, such as a null in a REQUIRED field, comes back as Rejected. The writer stays usable, and close() publishes every record that was accepted.

In contrast, if a write fails with an exception, close() discards the output instead of publishing a partial file. abort() lets you abandon a pending write deliberately, for instance when the job producing the data is cancelled.

Other writer improvements in this release include support for column and offset indexes (allowing page-level pruning when reading a file) and for Bloom filters. Bloom filters are space-efficient probabilistic data structures which can tell a reader with certainty if a given look-up key is not present in a row group, speeding up point queries (eq(), in()) against high-cardinality columns. They can have false positives though, i.e. the reader still needs to evaluate row groups passing the filter to determine whether the value actually is present or not. Bloom filters are written for the columns you name, with a false positive rate (FPR) of 1% by default. If needed, this can be fine-tuned per column (with a lower FPR resulting in a larger size of the filter):

Performance Improvements

Hardwood’s Parquet reader is significantly faster for many workloads as of 1.1.0.Beta2. In particular when reading files from remote object storage (S3), read times have been reduced by reworking how file segments are fetched:

  • Bloom filters are loaded in coalesced requests for multiple columns and/or row groups

  • Page indexes are only fetched for projected columns, and in addition one request covers several row groups

  • While a row group is read, the first column chunk of the next one is prefetched

  • Multi-file reads open each file only when the read reaches it, so time-to-first-result no longer grows with the number of files

There are also a number of improvements to query execution:

  • When a column is used for filtering but isn’t part of the projection (e.g. SELECT amount FROM events WHERE event_time >= T), the reader skips it entirely in row groups whose stats prove every row matches. This pays off for data sorted or clustered by the filter column, like querying a recent time window of an event log.

  • If a string or binary column is dictionary-encoded, predicates on it are executed in the dictionary space (evaluated once per dictionary entry instead of once per row), avoiding repeated comparisons of the same value.

In addition, there have been improvements to several decoders, the internal array sizing logic avoids the allocation of humongous arrays (which caused GC overhead), and more.

To ensure there are no performance regressions, we have set up a performance benchmark suite covering key workloads, which allows us to compare the results from two different Hardwood versions. Footer Caching and Reuse

When querying the same set of Parquet files repeatedly, for instance in a query engine opening a file once for each split it reads, or in a service opening a reader per request, re-parsing the same file footers on every open can become an overhead, as can the extra request needed for fetching large footers from S3. A footer only changes when its file is rewritten, so it can be cached, keyed on the file’s identity. This pattern is supported via the new MetadataSource extension point, allowing you to plug in custom caching logic. Here’s a simple in-memory example:

record FooterKey(String uri, String etag) {}
Map<FooterKey, ParsedFooter> cache = new ConcurrentHashMap<>();

MetadataSource footers = file -> {
    FooterKey key = new FooterKey(
            file.name(),
            file.identity().orElseThrow()); (1)

    ParsedFooter footer = cache.get(key);
    if (footer == null) {
        footer = ParsedFooter.readFrom(file);
        cache.put(key, footer);
    }
    return footer;
};
1 The file’s identity; for S3 objects, that’s the ETag, which changes whenever the object is replaced

Each footer retrieved from a custom source is checked against the file’s identity (e.g. ETag for S3InputFile) and its length before any data is read, and a stale entry will fail with StaleMetadataException. The footer caching API is experimental and may still change.

Id-Based Dictionary Access

Dictionary-encoded string and binary columns can now be accessed by id rather than by decoded column values, potentially yielding much faster processing, depending on the specifics of your business logic. As an example, let’s assume you have a 1BRC-style Parquet file with temperature measurements for a set of weather stations. The station names are dictionary-encoded, and we want to count the number of measurements per station. Instead of decoding the station name of every row and updating a hash map keyed by that String, the counts can be kept in an array indexed by each name’s dictionary id, resolving names only once per dictionary entry and batch:

Map<String, Long> rowsPerStation = new HashMap<>();
try (ParquetFileReader reader =
         ParquetFileReader.open(InputFile.of(path));
     ColumnReader station = reader.columnReader("station")) {
    while (station.nextBatch()) {
        int[] ids = station.getDictionaryIds(); (1)
        BinaryDictionary dictionary = station.getBinaryDictionary();

        long[] rowsPerEntry = new long[dictionary.size()];
        for (int i = 0; i < station.getValueCount(); i++) {
            rowsPerEntry[ids[i]]++;
        }
        for (int e = 0; e < rowsPerEntry.length; e++) {
            if (rowsPerEntry[e] > 0) {
                rowsPerStation.merge(dictionary.getString(e),
                        rowsPerEntry[e], Long::sum);
            }
        }
    }
}
1 For each value of the batch, its index into the current row group’s dictionary

For brevity, this assumes a column without nulls (a null’s id is -1) that is dictionary-encoded throughout; for batches without a dictionary, getDictionaryIds() returns null, and their values can be read via getStrings().

Also in This Release

Besides these key additions, the release contains a wide range of other improvements and fixes:

  • Filter predicates: isNull() and isNotNull() on struct, LIST and MAP groups; in() for every literal type except boolean; in and notIn in the parquet-java compatibility FilterApi

  • TIMESTAMP columns stored as FIXED_LEN_BYTE_ARRAY(12), spanning the years 0001 to 9999 at nanosecond precision, can be read, filtered and written

  • OutputFile.inMemory() writes a Parquet file to memory

  • CLI: the interactive dive TUI lets you jump to a given row or row group, and print/convert select the same rows with --skip and --row-group; schema -F AVRO and -F PROTO emit schemas which Avro and protoc accept; convert --format json writes nested values as JSON objects and arrays; the native binary reads ZSTD-compressed files

  • Several cases where filters returned wrong rows were fixed, e.g. for NaN values and unsigned integer columns

  • Fixes for projecting columns whose name contains a dot, and for S3 endpoints that name their default port

Check out the release notes for the complete list, including several breaking changes (most notably, a reworked exception model, and index-based accessors following the projection’s column order rather than the schema order) and the API changes report for all changes to the public API. See the 1.1.0.Beta2 milestone for the full list of all 165 resolved issues.
