Writing to S3, Parallel Writes, ALP: Hardwood 1.1.0.CR1 Is Out

When the first preview of Hardwood’s writer shipped with 1.1.0.Beta1, it came with two notable gaps: it was single-threaded, and it couldn’t write to S3. Both are closed now, and I’m happy to announce the first release candidate for Hardwood 1.1!

Besides rounding out the writer, this release brings support for the latest Parquet file format additions (ALP encoding, FILE logical type), and it substantially improves the performance of local as well as remote file reads. We’ve also hardened the reader against untrusted files and set up a nightly benchmark suite for catching performance regressions.

You can fetch the Hardwood library JARs from Maven Central. Binaries for the Hardwood CLI are available on the GitHub releases page. Let’s dig in!

Writing to S3 and Parallel Writes

Larger files are streamed to S3 as a multipart upload while they are written: whenever a part (8 MiB by default, configurable via uploadPartSize()) is full, it is uploaded in the background, with up to four uploads in flight while the writer continues with the next part.

The second big change to the writer is that it now makes use of multiple CPU cores. When a row group is flushed, its column chunks are encoded and compressed in parallel. By default, the writer uses one thread per available processor. If you want to control the number of threads, or share one thread pool between several writers and readers, pass a HardwoodContext when creating the writer, e.g. HardwoodContext.create(4) to use up to four threads, or create(0) to run all encoding and decoding work on the calling thread.

Further Writer Additions

Some other writer additions made it into this release:

  • For codecs like ZSTD you can now set the compression level, allowing you to trade write time for file size.

  • If your rows are sorted, you can declare the sort order via sortingColumns(). It is recorded in the metadata of each row group, so that query engines can take advantage of it. The writer verifies the declared order as rows come in, failing the write when a row is out of order.

  • Optionally, data pages can be written in the DATA_PAGE_V2 format, which keeps repetition and definition levels uncompressed and states each page’s row count in its header, letting readers skip pages or locate nulls without decompressing them.

Finally, StructBuilder.setValue() accepts values in the form the reader’s getValue() returns them, making it easy to copy rows from one file to another without having to dispatch on each field’s type.

New Format Features

Hardwood 1.1.0.CR1 supports two recent additions to the Parquet format specification. First, ALP (Adaptive Lossless Floating-Point), a new encoding for FLOAT and DOUBLE columns:

Many floating-point values in practice are decimals with a fixed, small number of fractional digits, such as prices or sensor measurements. ALP multiplies such values by a power of ten, turning for instance 12.34 into the integer 1234, and bit-packs these integers relative to the smallest one of each block of 1,024 values, so that the closer together the values of a block are, the fewer bits each one takes up. Values which can’t be represented that way are stored as-is, so the encoding is lossless.

ALP is currently marked as a preview feature in the Parquet spec, so make sure your consumers can read it before using it. Hardwood reads ALP-encoded columns, and writes them when requested:

Compared to Hardwood’s default encoding, ALP takes up 26% less space in this particular case. Writing the two columns into an in-memory file is five times faster with ALP and no compression1 than with the default encoding and ZSTD (85 ms vs. 443 ms), and reading them back almost four times faster (20 ms vs. 77 ms), measured on my little N300 box. That said, ALP isn’t a good fit for all kinds of floating-point data: columns with comparatively few distinct values are typically better served by dictionary encoding, so measure which columns benefit and enable ALP for those.

[1] ZSTD doesn’t shrink ALP-encoded data any further, as ALP already packs each value into the minimum number of bits, so compression can be skipped.

Second, the new FILE logical type for a group describing a binary object, such as an image or a PDF document, either stored inline or in external storage, referenced by a URI (optionally with an offset and size, e.g. pointing to an entry in a larger archive). Hardwood reads such groups as validated PqFile objects, and writes them via setFile().

Besides these spec additions, Hardwood now also supports field ids (as used by Apache Iceberg, Delta Lake and DuckLake to identify columns independently of their names), which are exposed on ColumnSchema and SchemaNode, can be set when building a schema, and are retained when rewriting a file.

Performance Improvements

To enable further improvements to Hardwood’s performance, we have decided to completely rethink how the fetching and decoding of pages is organized within the read engine. The idea is simple: a read is now split into small jobs, such as fetching a byte range or decoding a page. They are executed by a scheduler, which runs them in the order of the rows they serve. Fetching happens on virtual threads and decoding on the thread pool of the read’s HardwoodContext, so neither has to wait for the other. And as requests are capped at 16 MiB, decoding starts as soon as the first chunk of a column has arrived, keeping all cores busy. Further improvements include:

  • An S3 object of up to 256 KiB is read in the single request which opens it; for larger files, the footer and the page index usually come with that first request

  • Multi-file reads open the next files ahead of time, fetching their footers and first data while earlier files are still being read

  • Uncompressed fixed-width values are read in place from the page, and row readers projecting only flat columns take a faster path

  • Batches, dictionaries and decompressed pages no longer become humongous G1 objects on heaps below 4 GB, avoiding the associated GC overhead

To spot regressions early, we set up an automated performance benchmark suite. It runs every night, recording wall-clock time, CPU time, allocations and peak live set of each scenario, and uses Apache Otava to detect change points in the resulting time series, which are published on the benchmark results page.

I recently also re-ran the benchmarks from the 1.0 announcement on the N300, comparing Hardwood 1.0 and a recent development snapshot against the latest parquet-java (1.18.2). Also in This Release

To harden reads of untrusted files, the reader now validates every size, count and length a file declares before allocating anything based on it, failing with a ParquetReadException instead of allocating without bound. The parsing of footers and page headers, page decoding, and decompression are fuzzed with Jazzer.

Other notable changes include:

  • Reads fail with an exception instead of hanging when they can no longer make progress, e.g. after running out of heap

  • S3: public buckets can be read without credentials (S3Source.Builder.anonymous()), a read fails if the object was replaced after opening, and stalled responses are retried

  • Fixes for shredded Variants and for files using the deprecated BIT_PACKED level encoding

  • CLI: --log-file captures detailed logs, such as the byte ranges fetched from S3, and S3 reads fall back to unsigned requests when no credentials are configured

  • CLI releases ship with checksums and build provenance attestations, verifiable via gh attestation verify

This release contains a few breaking changes, most notably the new LogicalType.FileType and Encoding.ALP, which require an additional case in exhaustive switch statements over these types, and the new fieldId component of ColumnSchema and SchemaNode.GroupNode, so that schemas which differ only in their field ids are no longer equal. If you’ve used the writer of the 1.1 preview releases, note that WriterConfig now takes a Compression object and FileSchema.Builder and StructBuilder declare leaf columns via primitive(…​). Check out the release notes for details, and the API changes report for all changes to the public API. See the 1.1.0.CR1 milestone for all 157 resolved issues.

Wrapping Up

A big thank you to everyone who contributed to this release: Alex Petrov, Alex Sorokoumov, André Rouél, Arnab Nandy, Chandan Dhamande, Fawzi Essam, Jeronimo López, Manish, Matt Van Horn, Matthew Mullett, Omar Abdelmawgoud, ommkd, Perfloop Agent, and Rion Williams.

As for next steps, we’re planning to release a second candidate in about two weeks, with the public API of Hardwood 1.1 in its final shape, followed by Hardwood 1.1.0.Final as an early Christmas present before the holidays.

Beyond that, Hardwood 1.2 will bring a higher-level API for copying and transforming Parquet files, which copies unchanged data as-is and only re-encodes what a transformation touches, e.g. for compacting small files or dropping a column. Other potential additions include support for Parquet modular encryption, a strict memory quota for reads, and several additions around the VARIANT column type.

Until then, please give the release candidate a try, in particular the new writer features such as writing to S3, and let us know your feedback via GitHub issues and discussions!
